=== LOGIN FLOW (POST https://*.supabase.co/auth/v1/token?grant_type=password) ===

  Result: API returned 400 with
            {"code":"invalid_credentials",
             "message":"Invalid login credentials"}

  Initial finding (later corrected): destructive toast appeared "missing"
  on the rendered page. Closer DOM-mutation observation showed the toast
  DOES render correctly:
    role="status" / text "Sign in failed Invalid login credentials"
    visible from ~200ms after click.
  My earlier screenshot was taken at +6s, after Radix's default 5s
  auto-dismiss had already removed it.

  -> Not a bug, but the underlying UX is real:
     5 seconds is too short to read and act on an error message,
     especially for destructive variants like failed-credentials.

  Fix applied: src/components/ui/toast.tsx
  When a Toast renders with variant="destructive" and no explicit
  duration is passed, the component now defaults to 8000ms instead of
  Radix's 5000ms. Scope is app-wide (every error toast benefits),
  one-line policy change, types green (`npm run typecheck`),
  production build green (`npm run build`).

=== OPEN QUESTIONS FOR PRODUCT/ENG ===

  Issue #1 — /pricing is auth-gated   [RESOLVED 2026-06-02, commit ba9056e]
    Unauthenticated visitors were bounced to /login?reason=session-expired.

    Root cause: src/context/auth-context.tsx Effect 2 used isPublicPath()
    only — it ignored isOpenPath(), which is where /pricing already lived
    (via marketingPaths in src/lib/rbac.ts). The middleware (middleware.ts)
    correctly combined both checks; the client did not.

    Fix: one-line change in auth-context.tsx — the unauth-redirect branch
    now also passes through paths matched by isOpenPath(). Keeps /pricing
    in marketingPaths (so signed-in users still see it; no regression).

    Verified live: smoke test re-run after Vercel deploy returned
      OK  /pricing  200  h1=["Screen 200 CVs in the time it takes to read 10."]
    (was previously REDIRECT -> /login?redirectTo=%2Fpricing)

  Issue #2 — Perf: 1.2s Total Blocking Time on landing
    Performance score 74 is held back by main-thread work and JS
    execution time. Quick wins suggested by Lighthouse:
      - drop ~44 KiB of unused JS (likely dynamic-import the dashboard
        chunks that aren't needed on /login)
      - drop legacy polyfills (target newer browsers in next.config)
      - investigate render-blocking requests

  Issue #3 — Missing <main> landmark
    Accessibility 98/100 (one audit failure). The login layout wraps
    content in a <div>, not a <main>. Tiny fix in src/app/login/page.tsx
    or in the surrounding ClientLayout.tsx.
